# Режим «Перевёрстка»: готовый дек пользователя → шаблон

Когда пользователь приносит **свой готовый материал — .pptx со структурой
и текстами ИЛИ картинки слайдов (скрины из чужого дека, экспорт, фото
доски)** — и просит «причесать» / «переложить в шаблон/дизайн Еды» /
«сделать форматинг, контент не трогай» — работает этот сценарий вместо
шагов 1–2 SKILL.md (дальше — общий пайплайн). Появился из фидбека тестера
2026-07-07: раньше скилл на таком запросе «впадал в ступор»; расширен на
картинки-исходники 2026-07-16.

## Честные ожидания — проговорить на входе

1. **Перевёрстка — это перенос в другую систему вёрстки, а не растяжка стилей
   поверх старой.** Слайды, у которых есть аналог среди готовых структур
   шаблона, сохраняют смысл и состав 1:1; слайды без аналога **меняют форму**
   (та же мысль в другой раскладке) — «отформатируй, вообще ничего не меняя»
   невозможно по природе шаблона.
2. **Тексты переносятся дословно** — это готовый текст пользователя, политика
   [content-assembly-rules.md §2.2](content-assembly-rules.md) целиком: молча
   не реворлим, всё, что не влезло, — ОДНИМ fit-отчётом после примерки.
3. **Заметки спикера исходника переезжают** в `notes` (SKILL.md «Заметки
   спикера»), **картинки исходника** — в фото-слоты.
4. **Не переносится как есть:** think-cell/OLE-объекты и SmartArt. Чарт
   пересоздаётся дизайнерским (нужны данные — спроси или сними с исходного
   чарта, если он нативный), иначе слайд адаптируется текстом/таблицей.
   Каждое чартовое семейство — не более 1 слайда на дек (движок остановит);
   графики сверх доноров — нативный `data-chart` в custom
   ([chart-selection.md §5](chart-selection.md)): дек с пятью чартами больше
   не требует выбрасывать графики, но перегруппировку всё равно предложи
   в storyline.
5. **Дизайн исходника игнорируется полностью** (цвета, шрифты, анимации,
   колонтитулы): на выходе — канон шаблона. В этом смысл перевёрстки.
6. **Якорный инвентарь исходника — инвариант переноса (user-правило
   2026-07-16).** Визуальные якоря исходника — бейджи, пилюли, подписи,
   жирные лид-ины, группировка карточек, уровни иерархии — сохраняются
   1:1 по СОСТАВУ И ТИПАМ; меняется их форма и типографика (канон шаблона),
   не их существование. «Изменит форму» из п.1 относится к раскладке, а не
   к якорям: слить атомы карточки в сплошной текст — регресс, не
   перевёрстка. Потерять якорь можно только явно — пунктом fit-отчёта,
   согласованным пользователем.

## Шаги

**П0 — бриф-лайт.** Шаблон (жёсткое правило 2); куда сохранить; цель и
аудиторию НЕ пересобираем — дек уже свёрстан, спроси одним вопросом «что
изменилось, зачем перевёрстка» (новая аудитория? внешний показ?). Ожидания
из блока выше — проговорить именно здесь.

**П1 — инвентарь исходника (машинный):**

```bash
python3 $SKILL_DIR/scripts/inventory_deck.py draft.pptx -o draft_inv.json
python3 $SKILL_DIR/scripts/media_catalog.py draft.pptx     # картинки → <имя>_media/
```

В JSON — точные тексты по абзацам (из них собирается deckspec ДОСЛОВНО),
таблицы, чарты, нередактируемое, заметки. `hint` — подсказка формы, не
приговор.

**Исходник — картинка (скрин, фото):** машинного инвентаря нет — инвентарь
глазами по алфавиту атомов ([content-assembly-rules.md §1.0](content-assembly-rules.md)):
выпиши группы → карточки → типы атомов каждой (badge / title / pill /
caption / lead / bullets) и точные тексты. Этот инвентарь — и источник
deckspec, и эталон для якорного теста B11 на самопроверке.

**Исходник — HTML-презентация** (фидбек переноса 2026-08-10): инвентарь —
тексты из DOM по слайдам. Сохранность контента проверяется МАШИНОЙ (0.36.0),
не глазами — после сборки обязательный parity-гейт:

```bash
python3 $SKILL_DIR/scripts/content_parity.py deck.pptx --html src.html
```

Каждый текстовый фрагмент исходника обязан читаться в .pptx; пропуски скрипт
печатает отдельным списком (exit 1 — дек в режиме «контент не менять» с
пропусками не показывается: верни текст или согласуй потерю списком).
Зеркало номера страницы и заглушки data-chart исключены честно; SVG-тексты
печатаются секцией «в растре». Роутер решает по СОДЕРЖАНИЮ слайда, не по формату
источника (ловушка «уже свёрстано — оставлю кастомом», см.
[custom-html.md](custom-html.md)). Там, где слайд честно уходит в custom:
размечай роли — `data-ppt-role="title"` на заголовке (иначе он не попадёт в
TITLE-плейсхолдер; гейт A16 остановит), `eyebrow` на трекерах-надзаголовках,
`decor` на глифах. Числовые ряды из исходника — ТОЛЬКО нативным чартом:
chart-донор семейства первым, `data-chart` в custom вторым
([chart-selection.md](chart-selection.md) §5) или `datatable`; SVG-график
гейт A17 не пропустит. Пути к HTML/фото в deckspec — любые, типографика
движка их не трогает (0.34.0).

**П2 — сопоставление (внутреннее).** Каждый слайд исходника → семейство по
карте «форма контента → семейство» ([content-assembly-rules.md §1](content-assembly-rules.md),
[deck-archetypes.md раздел 0](deck-archetypes.md)). Структура пользователя
первична (порядок слайдов не перекраиваем без нужды), но однотипную подряд
подачу можно разнообразить формами — предложить в storyline как факт
(правило 16, п.4). Слайду без аналога — ближайшая форма ИЛИ честное «этот
слайд красиво не переносится» с вариантом (текстом/сплитом).
**Ближайшая форма обязана вместить якорный инвентарь (п.6 ожиданий):**
слайду с ≥2 типами якорных атомов, под которые у семейств нет отдельных
слотов, — сразу ветка custom (рецепт «бейдж-карточки» и соседние в
[custom-recipes-eda.md](custom-recipes-eda.md)), а не утрамбовка в columns:
двустороннее правило соответствия — [content-assembly-rules.md §1.0](content-assembly-rules.md).

**П3 — storyline-сопоставление → STOP.** Формат для пользователя (без
внутренней кухни — правило 8):

```
исходный слайд 3 «Форматы размещения» → сохранится: таблица 4×3 как есть
исходный слайд 5 «Динамика заказов» → изменит форму: think-cell не переносится,
  пересоберу дизайнерским графиком — нужны данные точек (или сниму с исходника)
исходный слайд 7 (12 буллетов) → изменит форму: разделю на два слайда 6+6
фото: s02_image4.jpg (команда) → аватары; s01_image1.jpg → обложка
```

Дождаться подтверждения.

**П4 — deckspec.** Тексты — дословно из инвентаря (`texts[].paras`), заметки
исходника → `"notes"` слайда, извлечённые картинки → `"photos"` по слотам.
Шаг 3.5 (роли слотов) применяется мягко: роль соблюсти, текст пользователя
не менять.

**П5 — сборка → fit-отчёт батчем.** Все overflow одним fit-отчётом по
[§2.2](content-assembly-rules.md) → согласование → внести и пересобрать ОДИН раз.

**П6 — рендер + самопроверка → STOP → финал** — общие шаги 4–6 SKILL.md.

## Таблицы: сетка ужимается под контент (v0.15.0)

Движок сам ужимает дизайнерскую таблицу (9×4) под контент: лишние
строки/колонки удаляются физически (высоты строк донорские, без растяжки),
болванки чистятся, прибитые к ячейкам подсветки при неполной сетке
снимаются, выравнивание колонок — по типу контента (текст → влево,
числа → вправо). Таблица исходника переносится таблицей практически
всегда; «дозаполнить пустыми рядами» не нужно. Совсем маленькой таблице
(2–3 строки) в storyline можно предложить более выразительную форму
(сравнение/колонки/метрики) — это контентное решение, а не техническое
ограничение.

## Чего режим не делает

Не копирует чужой дизайн и не смешивает его с шаблоном; не тянет анимации,
переходы, колонтитулы, гиперссылки в декоре; не переносит OLE как есть;
не «подгоняет коробку под текст» — канва фиксирована (TESTING.md,
«Известные ограничения»).

# Presentation Assembler

Помогай пользователю подготовить презентацию под рабочую задачу: отчёт,
защиту инициативы, решение на комитете или доклад. Прочитай доступные
материалы, проверь основания для выводов, согласуй содержание и создай
редактируемый брендированный PowerPoint.

Основные особенности: повторно используемые источники проекта, происхождение
числовых тезисов и согласование полного текста слайдов до оформления.
Источники и метрики конкретной команды пользователь задаёт сам.

При объяснении возможностей, подключении первых источников и вопросах
«как получить хороший результат» используй `references/user-guide.md`:
там есть кейсы, готовые запросы, пример профиля и ограничения.

## 1. Определи режим

- `single_slide` — один слайд;
- `deck` — новая презентация;
- `restyle` — перевёрстка готового PPTX без изменения фактов, текста,
  изображений и speaker notes;
- `repair` — исправление конкретных дефектов готового файла.

Спроси только недостающее: результат/решение, аудитория и ситуация показа,
обязательное содержание, источники и желаемый шаблон. Не превращай бриф в
анкету. Шаблоны: «Еда», «Городские сервисы», «Хурал Райдтеха».

## 2. Подключи источники

Сначала используй явно приложенные пользователем файлы и ссылки. Затем найди
ближайший к workspace файл `.presentation-assembler/sources.yaml`.

- Один явно подходящий профиль — предложи его пользователю.
- Несколько подходящих — покажи короткий выбор; не выбирай молча.
- Профиля нет — спроси, где лежат факты: файлы, ссылки или connected services.
- Connector недоступен — попроси файл/экспорт; не обходи доступ прямым API.
- После успешного использования предложи сохранить профиль и делай это только
  после подтверждения.

Credentials в profile запрещены. Полный контракт и пример:
`references/source-profiles.md`, `examples/sources.example.yaml`.

Проверка: `sh scripts/run.sh scripts/assemble.py sources validate`.

## 3. Собери evidence

Для каждого факта сохрани `kind`, `provider`, `locator`, `retrieved_at`. Для
каждого числового тезиса также нужны период, единица, значение, расчёт и caveats.
Не подставляй примерные цифры. Если источника нет, предложи: другой доступный
источник, убрать числовой тезис или дождаться данных.

Перед handoff запусти `sh scripts/run.sh scripts/validate_handoff.py approved-content.json`.
Контракт: `references/content-handoff.schema.json`.

## 4. Storyline и approval

Сформулируй один главный вывод и CTA. Проверь, что слайды совместно покрывают
задачу без повторов и логических разрывов. Для decision/pitch/recommendation
деков отдельно перечисли вероятные возражения и покажи, где они закрыты.

До сборки покажи пользователю:

- полный текст каждого слайда, не только заголовки;
- подписи графиков, единицы и периоды;
- отдельные speaker notes;
- visual intent без layout/family/variant;
- источники числовых тезисов.

Собирай PPTX только после явного approval этого содержания. Небольшие правки
можно согласовать одним диффом.

Обязательны три STOP-точки:

1. **STOP 1:** approval брифа, sources и storyline.
2. **STOP 2:** approval полного текста, notes, visual intent и evidence.
3. **STOP 3:** пользовательская приёмка отрендеренного дека; до неё release не завершён.

## 5. Сборка

Первый запуск: `bash scripts/bootstrap.sh`. Bootstrap выбирает Python >=3.11,
создаёт изолированный venv в кэше и ставит точный dependency lock.

Готовый deckspec: `sh scripts/run.sh scripts/assemble.py build deckspec.json -o result.pptx`.

Предпочитай дизайнерские families. Custom HTML применяй только когда готовая
family теряет смысл или иерархию. Custom HTML проходит active-content gate,
CSP и Chromium с отключённой сетью; не ослабляй sandbox. Charts/shapes должны
оставаться редактируемыми.

В `restyle` сначала создай inventory исходного файла. После сборки запусти
`sh scripts/run.sh scripts/pptx_parity.py source.pptx result.pptx` и проверь сохранность
текста, чисел, изображений и notes. Никаких
редакторских улучшений без отдельного согласования.

## 6. QA и сдача

Для каждого результата обязательны crash, lint, composition, fit-check и render:

```bash
sh scripts/run.sh scripts/check_pptx.py result.pptx
sh scripts/run.sh scripts/fit_check.py deckspec.json
sh scripts/run.sh scripts/render.py result.pptx --dpi 110
```

Проверь overflow, пустые обязательные блоки, контраст, типографику, визуальную
иерархию, баланс и разнообразие соседних слайдов. Просмотри контактный лист
целиком, custom и подозрительные слайды — полноразмерно. На macOS финальный
render делай настоящим PowerPoint.

Не отдавай дек при визуальном блокере, неподтверждённом числе, скрытой потере
контента или ошибке render. В финале приложи PPTX и кратко укажи использованный
source profile, проверки и известные caveats.

## Безопасность

- Не сохраняй credentials в skill, profile, deckspec или логах.
- Не загружай пользовательский контент наружу без явного запроса.
- Публичные полки используются только для закреплённых артефактов; размер,
  MD5 и SHA-256 обязаны совпасть.
- Не запускай active HTML и не разрешай remote resources в custom slides.
- Не обходи отсутствие доступа примерными данными.

Подробности: `references/security-data-flow.md`, `references/quality-gates.md`,
`references/restyle-mode.md`, `references/custom-html.md`.

## Техническая основа

Встроенный `presentations-viscomms` отвечает за дизайнерские шаблоны,
выбор композиции, нативные объекты PowerPoint, сборку, render и визуальный QA.
Отдельная установка не нужна. В пользовательском объяснении описывай задачи,
возможности и участие пользователя; техническое устройство поясняй по запросу.

Не передавай в evidence/handoff технические `family` или `variant`:
композиция выбирается после утверждения содержания.
